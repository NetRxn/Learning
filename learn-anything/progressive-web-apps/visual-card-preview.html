PWA Architecture :: TC1 Foundations

pwa-tc1-request-lifecycle-01 (basic) — diagram on back

Q: List the 5 cache layers a browser request passes through, from closest to the user to furthest.
A: 1. Memory cache (in-process, same-page resources)
2. Service Worker (Cache API intercept)
3. HTTP cache (browser disk cache)
4. CDN edge cache
5. Origin server

pwa-tc1-request-lifecycle-02 (basic) — diagram on back

Q: At what point in the browser request lifecycle does a service worker get the chance to intercept a request?
A: After the memory cache check but before the HTTP cache. The SW's fetch event fires, giving it full control: it can serve from Cache API, modify and forward the request to the network, or generate a response entirely. If the SW calls fetch() itself, that request then passes through the HTTP cache and on to CDN/origin.

pwa-tc1-sw-lifecycle-01 (basic) — diagram on back

Q: What are the 4 main phases of the service worker lifecycle, in order?
A: 1. Registration — browser downloads the SW script
2. Installation — install event fires, typically pre-caches essential resources
3. Waiting — new SW waits until all tabs using the old SW close
4. Activation — activate event fires, typically cleans up old caches; SW now controls pages

PWA Architecture :: TC2 Caching Strategy

pwa-tc2-strategy-04 (comparison) — diagram on back

Q: Compare Cache-First and Network-First: when does each strategy serve stale data, and what's the user experience tradeoff?
A: Cache-First: Serves stale data if the cache entry is outdated AND the URL hasn't changed (risk with non-hashed URLs). UX: instant load, but potentially stale.
Network-First: Serves stale data only when the network fails (offline/timeout fallback). UX: slower load (waits for network), but usually fresh. However, Network-First can ALSO serve stale data if the browser HTTP cache returns a cached response to the SW's fetch() call — the "HTTP cache trap."
analyze · concept

pwa-tc2-sw-http-01 (basic) — diagram on back

Q: Explain the "network-first hits HTTP cache" trap. Why does a network-first SW strategy sometimes return stale data?
A: When the SW calls fetch(request) to go to the network, that fetch request first passes through the browser's HTTP cache. If the HTTP cache has a fresh (unexpired) entry, the browser returns it without ever reaching the CDN or origin. So "network-first" actually means "HTTP-cache-first, then network." The SW thinks it got a fresh network response, but it came from the HTTP cache. Fix: use fetch(request, { cache: 'reload' }) to bypass the HTTP cache.

pwa-tc2-cdn-01 (basic) — diagram on back

Q: What is the "double-cache problem" when a service worker is combined with a CDN?
A: After a deploy, both the SW cache and the CDN edge cache may hold stale content. Even if the SW uses network-first, the "network" response comes from the CDN edge which may still serve the old version (CDN TTL hasn't expired). So the user gets: old SW cache → falls through to network → CDN serves old version anyway. Two layers of staleness must be coordinated — purging one isn't enough.
analyze · concept

pwa-tc2-appshell-01 (basic) — diagram on back

Q: What is the App Shell architecture pattern, and what problem does it solve?
A: App Shell separates a minimal UI skeleton (navigation, layout, loading states) from dynamic content. The shell is pre-cached by the SW and served instantly on every visit — the user sees the app frame immediately while content loads. It solves the "blank screen" problem: instead of waiting for HTML + JS + CSS + data, the user sees a familiar UI within milliseconds.
understand · concept

pwa-tc2-appshell-03 (comparison) — diagram on back

Q: Compare the caching approach for an App Shell SPA vs a server-rendered htmx application. What does each cache, and what strategy works best?
A: App Shell SPA: Cache the shell (HTML template + JS + CSS) with cache-first. Cache API data with network-first or SWR. Shell loads instantly, data fills in.
Server-rendered htmx: Cache complete HTML pages with SWR or network-first. Each page is a full document. Can cache previously-viewed pages for offline reading, but can't meaningfully separate shell from content. Offline creation of new pages requires fundamentally different architecture.

PWA Architecture :: TC3 Evaluation Framework

pwa-tc3-offline-01 (basic) — diagram on back

Q: What are the 3 tiers of offline strategy for a PWA, from least to most complex?
A: 1. Offline fallback page — Show a branded "you're offline" page instead of the browser's default error. Minimal effort, minimal value.
2. Offline reading — Cache previously-viewed content so users can re-access it offline (read-only). Moderate effort.
3. Offline-first — Full read/write offline capability with background sync. App works completely without network, syncs when reconnected. High complexity (conflict resolution, queue management).
understand · concept

pwa-tc3-update-01 (basic) — diagram on back

Q: Describe the recommended user-controlled update flow for a PWA (as opposed to skipWaiting).
A: 1. New SW installs in background (waiting state)
2. App detects controllerchange or checks registration.waiting
3. Show a non-intrusive notification (toast/banner): "Update available — click to refresh"
4. On user click: send postMessage('SKIP_WAITING') to the waiting SW
5. Waiting SW calls skipWaiting()
6. controllerchange event fires → app reloads

This gives the user control and ensures they don't lose unsaved work.

pwa-tc3-fitness-01 (basic) — diagram on back

Q: What are the 5 dimensions of a structured PWA fitness evaluation?
A: 1. Offline strategy tier — What offline capability does the app need? (fallback/reading/offline-first)
2. Platform constraints — Are iOS limitations deal-breakers for the target audience?
3. Update flow — How critical is version freshness? What's the cost of stale content?
4. Architectural compatibility — Does the current architecture (SPA/SSR/htmx) support PWA features?
5. Migration cost vs. value — What does PWA add that the current app doesn't have, and is it worth the effort?

PWA Architecture :: TC4 Quality Detection

pwa-tc4-migration-01 (basic) — diagram on back

Q: What are the 4 levels of PWA migration complexity, from easiest to hardest?
A: 1. Add-on PWA (1-2 days): Add manifest + basic SW to existing app. Installability + offline fallback page.
2. Caching PWA (1-2 weeks): Add intelligent caching strategies per resource type. SWR for pages, cache-first for assets. Offline reading.
3. Offline-capable PWA (1-3 months): Full offline read/write with background sync, conflict resolution, IndexedDB state management.
4. Architecture migration (3+ months): Restructure from server-rendered to client-side for App Shell pattern or offline-first.

PWA Architecture :: TC5 Advanced Topics

pwa-tc5-push-01 (basic) — diagram on back

Q: Describe the full pipeline for Web Push notifications: what components are involved and how do they interact?
A: 1. Client requests permission, subscribes via Push API → gets a PushSubscription (endpoint URL + keys)
2. App server stores the subscription, later sends a push message to the push service (e.g., FCM for Chrome, WNS for Edge) using VAPID keys for authentication
3. Push service delivers the message to the browser
4. Service worker receives the push event (even if the app/browser is closed)
5. SW must show a Notification (browser requirement — can't silently receive pushes)
6. User interacts with notification → notificationclick event → SW opens/focuses the app
